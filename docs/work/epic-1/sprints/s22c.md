# S22C · Cancellation of a registered position wait

**Track:** full, critical · **Needs:** S22 · **Contract:** the existing
[`WaitForPositionAsync` guarantee](../../../decisions/session-consistency.md#explicit-local-position-wait).

- **Goal.** A registered wait returns cancellation if the token was cancelled
  before the target was published, even when another callback delayed its
  cancellation notification.
- **Evidence.** On `4ee9d4a2`, a public wait remained pending with the token
  cancelled and the master below the target. An independent two-insert batch
  then published the target. The wait returned success while a second
  cancellation callback was held. The same ordering occurred with `Cancel` and
  `CancelAsync`. Completing cancellation before the write gave the expected
  cancelled result. Both inserts were visible in every case.
- **Acceptance.** Independently control registration, cancellation delivery and
  publication. Assert cancellation with the supplied token in the failing order,
  success for an uncancelled waiter on the same target, and publication of the
  independent batch. Keep the existing deadline, fault, close and held-Wake
  cases. A forwarded write with a confirmed master result keeps its existing
  completion rules. On a missed deadline the child reports
  `SynchronizationTimeout` and `CommittedPosition` and describes the missed
  deadline. Its position can already have advanced when the error is observed.
- **To read.** [S20I](s20i.md#s20i--investigate-the-debug-timeouts) and
  [the position clock](../../../design/write-path.md#waiting-for-a-published-position).
  Compare the existing clock-waiter scenario with the exact parent if the
  publication path changes.
- **Out of scope.** The pending-target index redesign belongs to S34. The
  historical timeout investigations keep the reopening conditions recorded in S20I.

## Tests first

The exact tests-first commit, `d494d860c850afce0eca4eee1b0c7e16bab7dc71`, passed
independent review with no findings. The reviewer traced registration, cancellation
request, delayed callback and batch publication separately for `Cancel` and
`CancelAsync`, and confirmed that the forwarded-write timer is armed after the master
reply. The hardest part was distinguishing coherent publication from notification
on both paths. The new tests control each event without adding an engine hook.
All three cases failed for the expected reasons when activated against `159d3fee6`.
The committed tests-first tree passed the Release build, format check and full suite
with 3,764 passed and 131 skipped.

## Implementation and independent probes

The first code review approved `e79bfe7e`. The hardest point was ordering the
authoritative close or fault mark, first reach and the token request across separately
delivered signals. An independent breaker then found a failure on the same head.
When the token request preceded both expiry and publication and the cancellation
callback was held, delivering the timer before publishing the target still returned
`SynchronizationTimeout` to the cancelled waiter. The uncancelled waiter on the
same target timed out correctly, and the independent write then published it.
The test-only follow-up `4f5b5382a58817b5286619211b79f98ff75202d5` passed independent
review. It holds publication until after both waits settle and uses the session
overload for the cancelled waiter. With its skip temporarily removed, it reproduced
the incorrect timeout twice on `e79bfe7e`. The tests-first assertions were retained.

The second independent code review closed on `6049c2fe165616fe56859686f46ba500a5c49e24`.
A registered waiter checks lifecycle state, then checks the supplied token before
using reach time, master loss or expiry. A forwarded write still reports its committed
position when application misses the deadline. The message describes the deadline even
if the position is already visible. Publication, `Wake` and the already-satisfied
fast path use the same code as the parent. The brief did not require a `clock-waiters`
comparison because publication did not change.

The independent breaker ran 12 probes on that exact head in Windows x64 Release and
Debug. All passed in each configuration. The probes covered callback, timer and Wake
delivery order, timely and late publication, expiry before publication, close and
fault, and confirmation of a forwarded write and its session position. The three
historical timeouts keep their separate reopening conditions in S20I.

The coordinator built the same head in Windows x64 Release and Debug with no warnings
or errors. Each full suite passed 3,768 tests with 129 skips. The Release format check
and all 18 samples passed. The sprint closed after two code review rounds and
repeated breaker probes, with no open findings. The S22 architecture dispositions are in the
[refactoring backlog](../../refactoring.md#architects-review-after-s22-25-november-2026).

## Part 2 · A fault marked before a cancellation request

- **Goal.** Finish the existing lifecycle check for a registered position wait.
  The architecture review after PR #77 reproduced a P2 on Release at
  `5dfb7384ea3c3adc829ebc1f4b6deb23b7d863cd`. With the fault mark visible before
  cancellation was requested and both notifications held, the clock returned
  cancellation when the token callback ran first and `Unavailable` when the clock
  was notified of the fault first.
- **Contract and sources.** The existing public
  [position wait](../../../decisions/session-consistency.md#explicit-local-position-wait)
  and the [clock's lifecycle check](../../../design/write-path.md#waiting-for-a-published-position)
  apply. This critical full-track correction precedes S23.
- **Acceptance.** On the exact parent above, add tests first in
  `ChildPositionDeadlineTests` through a child's public `WaitForPositionAsync`.
  Establish registration before injecting the fault. Hold notification of the
  fault and delivery of the wait's token callback independently. Observe the child
  in `Faulted` before requesting cancellation and confirm the wait is still pending
  with both notifications held. Run each delivery first in a separate case and
  observe `Unavailable` before releasing the second notification. On a healthy child
  a registered wait that ends through its token callback preserves the supplied token.
  Keep the existing results for publication, timer delivery and the deadline.
  If the publication path changes, compare `clock-waiters` on the exact parent
  and head.
- **Breaker targets, in order.** Probe the fault mark before cancellation under both
  notification orders, cancellation with the original token on a healthy node, and
  the existing publication, timer and deadline controls.
- **Scope.** The two requests in the new fault cases have an established order.
  The three historical timeouts retain the reopening conditions in
  [S20I](s20i.md#s20i--investigate-the-debug-timeouts).

The independent plan review closed without findings. The hardest part was keeping
the order of the fault mark and cancellation request distinct from the two possible
orders of notification. The existing publication, timer and cancellation holds
allow the tests to establish that distinction through the public wait.

### Tests first

The independent tests-first review of `a1bf23cdfcca50ad8b351fbd3183f22042713db9`
closed without findings. On Release with the engine from the exact parent, the
activated cancellation-first case returned `TaskCanceledException` while the
fault notification was still held. The clock-first case returned `Unavailable`,
and the healthy child preserved its supplied token. The hardest part of review
was verifying that the second notification stayed held until the result. A
continuation flag shows when the clock's hold ends. The test awaits cancellation
completion to detect expiry of the token callback's hold.

The coordinator's Release build, format check and full suite passed at that
tests-first commit with 3,770 tests passed and 130 skipped.

### Implementation and verification

The independent code review closed in one round without findings on
`af2790745a7cb58e299e130697233755f743524c`. The hardest part was following
the two ways the wait resumes through the task and confirming that both now apply
the same lifecycle check and clean up the registered target. When the token's
callback resumes a registered wait, the clock checks lifecycle state before it
propagates the original cancellation. All tests-first assertions were retained.
Publication and Wake use the same code as the exact parent, so the
`clock-waiters` comparison was outside this correction's acceptance condition.

The independent breaker ran 13 probes and 35 existing position tests at that
head in Windows x64 Release and Debug. All 48 passed in each configuration. A
separate Release repeat passed all 13 probes. The probes covered both notification
orders for pending and already-published targets, typed session reads, the
healthy token and an unaffected waiter, and timer and Wake delivery with first
publication before, at and after the deadline.

The coordinator built the same head in Windows x64 Release and Debug with no
warnings or errors. Each full suite passed 3,771 tests with 129 skips. The
Release format check and all 18 samples passed. The second part closed without
open findings. None of the three historical timeouts recurred in these runs.

The narrow review after part 2 kept the pending-target work in S34.
`HeldPublication` is shared by the position, replication, update and view
tests as well as the batch tests. A standalone move to the engine test
namespace would only change imports. Move it with the next reorganization
of those fixtures. The separate close finding and its evidence appear in
[the close correction](s23.md#close-and-pending-position-waits).
