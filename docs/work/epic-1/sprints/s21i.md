# S21I · Protected List traversal

**Track:** full · **Needs:** S21 · **Decisions:** [Q06.2](../../../decisions/memory-and-access.md) · **Owners:** E08, E05

- **Goal.** Explain and reduce the cost of a full packed List traversal under a
  protected view. Preserve the caller's read epoch, the stored order and zero
  managed allocations for a fixed-width scalar traversal.
- **Contract.** S21's existing public surface and error contract apply. The
  enumerator reads the same revision even across a chunk boundary after a
  replacement. An enumerator copy advances independently and a value already
  obtained from `Current` can be read while the viewer is still active. Before
  the first successful move or once `MoveNext` returns false, `Current` raises
  `InvalidOperationException`. The indexer, Map and Set operations, and owned
  reads retain their S21 semantics.
- **Acceptance.** Validate the order and actual physical forms of Int64 Lists
  at 8/9 elements (inline/block), 512/513 (block/one chunk) and 8,188/8,189
  (one/two chunks). Exercise empty and descriptor-bearing Lists. For a nullable
  Int64 List with stride 9, ordinal 7,278 splits the scalar at byte 65,504
  and ordinal 36,391 has the null bitmap before the fifth boundary and the
  entire scalar after it. Compare the traversed values, including actual nulls
  and the adjacent entries, with independently expected values, the indexer,
  and an owned copy. A fixed-width Owned entry with two bitmap bytes and stride
  31 at ordinal 2,113 places its second bitmap byte in the tail. Exercise a
  nullable field there and the start of the scalar data. Under a held viewer,
  complete a replacement, keep the old chunks alive until release, and cross
  the first boundary through both the original and copied enumerators. Test
  `Current` before and after a traversal, as well as the retained element across
  moves. Assert exactly zero managed allocations after warm-up. Compile against
  the public assembly to verify the accepted local use and refusal to return
  the enumerator or `Current` from a scoped view.
- **Measured.** Repeat the original by-name owned Get and sum against the
  protected traversal at 1,000 and 100,000 Int64 elements. Compare each candidate
  with the exact S21I parent `5c1a1c4e` and an independent build of it for the gauge.
  Use the same warm-up, verified sums and allocations with six rotated process
  orders. An effect requires a paired median outside the gauge with a 3 percent
  floor and five of six paired directions agreeing. Include the original short
  view and ordinary owned-read controls. Record the supported causes and
  residual differences per platform with the emitted hot callers and the
  independent measurement review. An ARM64 rental requires the owner's approval.
- **Out of scope.** Public API additions, typed views, storage or wire format
  changes, and changes to publication or reader protection.

## Bounded study and candidate boundary

The current owned Packed List path opens its directory once, advances across
spans by record stride, and uses the shared scalar codec. The S21 protected
enumerator resolves an entry from its ordinal on every `Current`. For a
100,000-element Int64 List this entails 100,000 directory and 100,000 chunk
resolutions through the current source path. Its 13 chunks contain whole
Int64 values. JIT evidence and isolated runs are required to attribute the
elapsed difference. [Owned ReadPacked](../../../../src/Moltaro.Lattice.Engine/Storage/Roots/NestedValues.cs)

The .NET SequenceReader borrows the current span and advances to the next at
a boundary. Its binary extensions use the current span for a fixed-width read
and gather only a split value. The sources were consulted under MIT.
[Span traversal](https://github.com/dotnet/runtime/blob/60629d14374c56f1cb51819049ad1fa529307f8d/src/libraries/System.Memory/src/System/Buffers/SequenceReader.cs#L170-L192)
[Boundary handling](https://github.com/dotnet/runtime/blob/60629d14374c56f1cb51819049ad1fa529307f8d/src/libraries/System.Memory/src/System/Buffers/SequenceReader.cs#L259-L301)
[Binary reads](https://github.com/dotnet/runtime/blob/60629d14374c56f1cb51819049ad1fa529307f8d/src/libraries/System.Memory/src/System/Buffers/SequenceReaderExtensions.Binary.cs#L23-L49)

Arrow's execution path passes spans per chunk to its compute kernels. Its
random access and whole-kernel ownership are separate concerns. The source
was consulted under Apache-2.0. The study takes the traversal patterns
from these sources. It adapts no code.
[Batch spans](https://github.com/apache/arrow/blob/272715f6df2a042d69881ffa03d5078c58e4b345/cpp/src/arrow/compute/exec.cc#L349-L441)
[Kernel execution](https://github.com/apache/arrow/blob/272715f6df2a042d69881ffa03d5078c58e4b345/cpp/src/arrow/compute/exec.cc#L1047-L1093)

The first experiment caches a resident block for sequential traversal while
keeping scalar dispatch. The narrower implementation candidate exposes one
internal operation,
`ViewPackedBlock ReadPackedListBlock(ViewCollection collection, int block)`,
using the existing `ValueBlocks` resolution rules.
The borrowed block has a stride and no additional holder. The cursor advances
only within the viewer's epoch. A zero stride selects ordinary `Entry` for
descriptor records. Ordinary `Entry` also supplies the two parts of a split
record. A packed Owned entry with no descriptors uses the packed traversal.
The x64 six-pair check selected the one-boundary cursor as the first correction.

## Windows x64 results

The exact original-window repeat used S21I parent `5c1a1c4e`, an independent
build of it for the gauge and final source `c9e0cd8c`. All six paired view
times fell at both sizes, with zero managed bytes per traversal.

| Int64 List size | Parent view | Final view | Final owned | Paired final view / parent view | Paired final view / final owned |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 32.927 µs | 13.860 µs | 17.508 µs | 0.4120 | 0.8442 |
| 100,000 | 3.057 ms | 1.301 ms | 0.335 ms | 0.4107 | 4.0035 |

For the paired final view time divided by the parent view time, the gauge
intervals were 0.686086–1.457542 at 1,000 elements and 0.852528–1.172983
at 100,000.

The warmed repeat confirmed the improvement in all six pairs at each size,
with paired final-to-parent ratios of 0.5614 and 0.4273. Each comparison uses
the paired windows of its own repeat. The original short entry and held and
unheld Replace timings, the owned List timings, and all 16 ordinary owned
read-by-key timings stayed within their gauges. Some control bands were wide,
so those comparisons establish no timing change at this resolution.

The address-only experiment dropped two arena payload resolutions per entry
to two per traversal at 1,000 elements and 14 at 100,000. The selected cursor
resolves the directory and a chunk together at each boundary, for two and
26 respectively. It makes no per-element `Entry` call for the aligned Int64
rows. The separate 100,000-element factorial run measured 0.4663 for the
address cache alone. The Int64 scalar dispatch experiment used the same codec
and was neutral on its own at 0.9297, but measured 0.6995 compared with the
address cache alone. The outcome depends on the address path. The generic
null-check fusion and per-value prebinding alternatives each missed the
incremental criterion against the selected cursor, including in the separate
non-List scalar controls. They were left out.

The final hot loop still builds a value view for each element, checks its
declaration and nullability, and reads the scalar through the schema layout.
The owned path decodes whole spans into the typed collection and then sums
its typed values. The source and tiered x64 listings show this remaining
difference in work without resolving its individual timing contributions.

A separate warmed diagnostic used the earlier one-boundary cursor scratch
build, its block resolver and the same protected acquisition. It checked
the nonnullable Int64 declaration once and the shape of each chunk, then
summed the borrowed native values without projecting individual views.
Medians fell from 16.260 to 4.294 µs at 1,000 elements and from 1.249 to
0.055 ms at 100,000. Paired ratios were 0.2496 and 0.0414, with all six pairs
below their lower gauges of 0.89984 and 0.84385.
Both paths returned equal sums and allocated zero managed bytes. The
measured specialized scan cost applies to this Int64 fixture and isolates
the per-element API route as a substantial remaining cost. The specialized
sum is diagnostic only.

The final source `c9e0cd8c` closed the P3 from production review. Tests from
`0845cc7f` kept their assertions. Debug and Release built cleanly and each
passed 3,731 tests with 129 expected skips. Format and all 18 samples passed
and the independent breaker passed both probes after the P3 fix.

## ARM64 results

The verified archive reported exit 0 after a 532.4-second queue on Ubuntu
ARM64, with 16 logical processors, .NET SDK 10.0.404 and runtime 10.0.15.
The CPU was idle in the initial samples. The 20-worker entry row
oversubscribed the machine and is descriptive.

The original-window repeat used exact parent `5c1a1c4e`, its independent
gauge build and exact final source `c9e0cd8c`. All six paired view times fell
at each size, and every timed view row allocated zero managed bytes.

| Int64 List size | Parent view | Final view | Final owned | Paired final view / parent view | Paired final view / final owned |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 60.233 µs | 27.401 µs | 12.864 µs | 0.452570 | 2.1813 |
| 100,000 | 5.995 ms | 2.689 ms | 0.666 ms | 0.447442 | 4.0874 |

For the same paired comparison, the gauge intervals were 0.950818–1.051726 at
1,000 elements and 0.957119–1.044803 at 100,000.

The owned sums allocated 8,152 B and about 800,278 B respectively. Short
entry, held and unheld Replace, owned List sums and all 16 ordinary owned
read-by-key timing metrics were inside their numeric gauges. The seven
owned FullOpts listings were byte-for-byte equal between parent and final
source. The exact Release view suite passed all 32 tests, including all
10 traversal cases, with no skips.

The separate warmed factorial used the same Int64 sum workload on
experimental builds of the parent. Its combined build applied the scalar
dispatch diagnostic to the earlier address cache. The original-window
repeat above measured the exact final cursor. Each ratio below is a
paired median from the factorial repeat.

| Int64 List size | Address / parent | Scalar dispatch / parent | Both / parent | Both / address |
| --- | ---: | ---: | ---: | ---: |
| 1,000 | 0.489742 | 0.866645 | 0.310482 | 0.634329 |
| 100,000 | 0.483900 | 0.868724 | 0.312592 | 0.641639 |

Each paired median was below the lower gauge and all six paired times
fell. The gauge used the 3 percent floor. The scalar-only effect crossed
the ARM64 gauge and stayed within the x64 gauge. Adding scalar dispatch
after the address cache lowered the paired times on both platforms. These
measurements apply to the fixed Int64 diagnostic. The source and tiered
listings identify the remaining per-element projection, checks and scalar
access. The records do not assign elapsed time to individual checks or calls.

The implementation retains the block cursor and the general per-value
read contract. The specialized diagnostic variants stay outside the
product. The remaining time and allocation tradeoff is specific to the
matched by-name List sums. These runs did not judge release gates.

The raw timing, allocation, rotation, JIT and test evidence is kept
outside Git. The independent reviewer verified the final Windows x64 and
ARM64 results and their disposition under [Step 6](../../process.md#a-sprint-on-the-full-track).
No measurement finding remains open.
