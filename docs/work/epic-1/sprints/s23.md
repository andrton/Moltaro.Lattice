# S23 · Compaction and shrink

## Close and pending position waits

**Order and owner.** E07 owns this separate full-track correction at the first
boundary after the independently tested List append change. It precedes the
remaining S23 storage work, including the background maintenance lifetime.

**Existing contract.** A registered position wait that is still undecided when
`Closed` becomes visible ends in `Unavailable`. A result already decided before
close remains available to a caller that observes it later. Successful completion of
`CloseAsync` establishes that the instance has released its native memory.

**To read.** [Session consistency](../../../decisions/session-consistency.md#explicit-local-position-wait)
(14 November 2026), [memory and access](../../../decisions/memory-and-access.md) (24 November 2026
amendment), and [OneCloseTests](../../../../src/Moltaro.Lattice.Engine.Tests/Engine/Protection/OneCloseTests.cs).

**Acceptance.** Control publication of the public state separately from delivery
of the close notification to the waiter. After observing public
`Closed` while a registered wait is still below its target, deliver cancellation
or publish the target. Verify `Unavailable` for cancellation, wake and timer.
Preserve ordinary cancellation on an open instance, the earlier decided result,
and `ObjectDisposedException` on a fresh call after close completes. Verify that
a held protected read can keep native memory alive during close and that the
allocator has no outstanding allocations when close completes. Correct the XML
documentation of `LatticeDatabaseStateEnum.Closed` to distinguish the public
state from teardown completion.

**Evidence on `882b5b09`.** A research-only pause after `EngineDatabase.CloseAsync`
set `Closed` and before `PositionClock.Close` marked the clock reproduced both
wrong outcomes on a waiting child. Later cancellation returned its token. Later
publication returned success through either wake or timer. All six observation
probes ran in Debug and Release. With the pause disabled, a held protected read
kept one native allocation alive in `Closed`. The allocator held none after close
completed successfully. The probe and its raw runs are kept outside Git.

## Close and new write admission

**Track:** full · **Owner:** E07 · **Base:** `72899d5f2041e7b7e2cc086612b8ae2dc6919964`

**Goal and contract.** By the time either role exposes `Closed`, it has stopped
admitting new writes. A valid asynchronous write started through an existing set,
or a commit of a prepared batch, then returns a task that fails with
`ObjectDisposedException`. Obtaining a set or preparing the values or batch before
close does not start a write. Writes already admitted retain their
[`CloseAsync` outcomes](../../../../src/Moltaro.Lattice/ILatticeDatabase.cs). A successful
close completes after native memory is released.

**To read.** The earlier S23 close correction above, the XML for
[`ILatticeSet<TEntity>`](../../../../src/Moltaro.Lattice/Access/ILatticeSet.Generic.cs),
[`ILatticeSet`](../../../../src/Moltaro.Lattice/Access/ILatticeSet.cs) and
[`ILatticeWriteBatch`](../../../../src/Moltaro.Lattice/Access/ILatticeWriteBatch.cs),
the [write path](../../../design/write-path.md), [session consistency](../../../decisions/session-consistency.md)
(14 November 2026) and [memory and access](../../../decisions/memory-and-access.md)
(24 November 2026 amendment).

**Acceptance.** Hold close just after publication of `Closed`, before the clock
notification and teardown. Issue a valid asynchronous insert through a set obtained
in `Ready`, once on a closing master and once on a closing child. In each case the
call returns a task and awaiting it reports `ObjectDisposedException`. After the
observing child consumes its master's orderly end, it still has the same position
and no new row. For a closing child, observe its connection to the end, verify that
it sent no write request, and check the live master's position and absence of the row.
Exercise the distinct commit entry once with a nonempty batch prepared in `Ready`
and submitted after `Closed`; require the same task refusal and absence of effects.
Both batch roles converge on the same
admission mechanisms as their respective single writes. Use the existing controls
for a started master write (including its published result on a child), the three
outcomes of a forwarded write during child close, registered position waits and
cached reads, and an outstanding protected read whose native memory is released
before successful close completion. Add a control only where the existing suite
cannot distinguish a changed outcome. Check the exact tests-first commit on the
base behavior and then the exact implementation head. Reconcile the public XML,
README and engine design with the distinction between refusal of new operations
at `Closed` and release of native memory at successful `CloseAsync` completion.

**Measured.** If the ordinary write path changes, compare the affected role on the
exact base and candidate with equivalent warmed Release workloads. Hold workload
and setup fixed, alternate run order, and report latency or throughput, allocation
where applicable, and spread. An effect that does not exceed run-to-run variation
is inconclusive. Inspect the unaffected path when admission only moves work into
close. Record the cause and disposition of any confirmed loss.

**Breaker targets.** New local writes after public `Closed` on both roles and a
prepared batch; an already admitted master write and the outcomes of child requests
at different stages of delivery; preservation of cached reads, registered waits
and native-memory teardown. Establish the order with gates.

**Base observation.** The architect's review at `72899d5f` identified the gap in
write admission. A separate study held close just after `Closed` on the exact
base. A valid insert issued through a previously obtained set returned `Changed`
on each role and advanced the position from 0 to 1. For a closing master, the
live child reached that position and read the new row. For a closing child, the
live master committed and exposed the row. The already admitted master write
reached its ordinary result. Fresh calls after `CloseAsync` completed received
`ObjectDisposedException`. All three probes passed in Windows x64 Debug and
Release. The study and its raw runs are kept outside Git.

**Out of scope.** A new public state, load limits, a policy for simultaneous close and
submission, Q66, compaction, and reconnect or reload in S34.

## Storage work

**Collection edit cost carried from S20.** In the original `EditedList.Apply`, each append
to an initially empty List scanned every run created by earlier appends in that
update. For 8,000 appends the loop visited 31,996,000 runs before placement.
The sprint removes this repeated scan. Compare two counts of append commands
within one update on the parent and the fix, including the 8,000-append case.

**Resident collections carried from the S22 architecture review.** Follow the
[S23 resident collection shape entry](../../refactoring.md#s23-resident-collection-shape)
when compaction and shrink first let the same logical count have different layouts.

**Carried from S13, the first question of the study of this sprint:** a root names a
shared text entry by its address, so the roots that name an entry cannot be found from
the entry and it cannot be moved cheaply. Choose between leaving shared entries in place
(Valkey never moves an object with more than one reference), regions of their own for
entries, or an address table then — with the figure of what entries that are not moved
cost G1 after churn.

**Carried from S09, part 2:** compaction never moves a prepared block and takes its turn
under the lock of the writes or by the rule this sprint states.

**Index text ownership (F8).** S23 kept the reference held by each index node
for each of its shared text keys. A text move updates the stable locator and
preserves that ownership. The independent final indexed-text probe kept the
view and export across a relocation on both roles, checked the reference count
before and after the drain and checked index lookup after deletion and recreation.
See the [index lifetime rule](../../../design/ordered-index.md#text-references) and the
[F8 disposition](../../refactoring.md#found-while-coordinating-s14-part-2-20-november-2026).

**Track:** full · **Needs:** S22C · **Owners:** E01, E03 · **Closes:** Q17

- **Goal.** A database that changes for a long time with a constant amount of live data
  keeps a bounded amount of memory.
- **Contract.** None public. Internal: bounded moves of one block per step, collection
  shrink, release of empty segments, movement of shared text through its stable entry.
  The measurement program gains the churn trace of the fixture.
- **To read.** [Reader protection, publication and compaction](../../../design/milestone-1-engine-contract.md#reader-protection-publication-and-compaction);
  [Q17, all four parts](../../../decisions/allocation-and-compaction.md);
  [arena protocol, reclamation and relocation](../../../design/arena-protocol.md#reclamation-and-relocation);
  [memory accounting](../../../design/storage-and-maintenance.md#memory-accounting-and-evidence).
- **Acceptance.** Under churn with a constant live set — replace with other sizes,
  delete and reinsert, collection growth and removal — retained memory stops growing and
  the counters equal an independent tally. A reader of an entity being moved, by copy or
  through a view, always sees a coherent value; index entries and text handles stay
  valid across a move. An entity reserved by a write is not moved. Compaction starts on
  a region below half occupancy and moves one bounded block per step. A collection whose
  capacity stays above four times its need for 5 seconds shrinks to at most twice. Empty
  segments beyond the reserve of one are returned. Appending to a List in one
  update does not walk earlier runs to locate its end. Element order and the
  result of each command match an independent list, and a child applying the
  update reaches the same contents.
- **Measured.** Early figure for G5: peak against steady memory of one MemoryOnly node
  during the churn trace. Reported: compaction step time against its 1 ms budget; reader
  p99 with compaction on and off.
- **Out of scope.** Refusing writes at the memory budget (S24), the
  [segment evacuation trigger](s23a.md#s23a--evacuate-nearly-empty-segments), and
  manual maintenance commands, which are outside the milestone.

**Carried from the architect's review after S13 (18 November 2026).** Block kinds of
their own for the directory and the chunks of a text entry are decided here, where
something first has to tell them apart: today all three are of the kind of shared text
and only the length in the slot of the text table says which form an entry has. The
referrers of an entry cannot be found from it, and from S14 an index may be among them.
The slot array and the bucket table of the text table never shrink.

**Memory carried from S17.** Identify the holders of addresses that compaction may move.
In the churn trace, distinguish retained managed capacity from arena bytes. Include
publication scratch, batch claims, the child's key set and connection buffer where the
workload exercises them. S23 owns the shrink of the text table's slots and buckets after
a refused batch or after live texts are removed (V2 in the [refactoring backlog](../../refactoring.md)).
S24 owns budget accounting. S33 owns the transaction buffer's retention policy.

**Added by the planner on 24 November 2026, from the architect's review after S18.** A block of records has the kinds Value and Chunk, as a Binary has, so a move cannot
tell from its header whether a block holds children without climbing to its root: kinds of
their own are decided here, with the kinds of text entries already carried to this sprint.

## Part 1. Resident descriptor candidate

Test the aligned word inside the existing 16-byte descriptor before choosing
the representation. The following methods are an internal candidate in
`Storage.Values.ResidentDescriptor`.

| Method | Contract |
| --- | --- |
| `ValueDescriptor Read(ReadOnlySpan<byte> place)` | Decode a resident native slot. Read its address word with acquire semantics. The caller holds the read epoch or the lock of the writes. |
| `void Write(Span<byte> place, in ValueDescriptor descriptor)` | Encode a descriptor in a prepared native slot before it becomes reachable. |
| `void PublishLocation(Span<byte> place, ArenaAddress destination)` | Under the lock of the writes, publish one new location with a release store after the destination is ready. The caller owns the edge and the native lifetimes. |
| `uint ReadLength(ReadOnlySpan<byte> place, int blockOffset)` | Read immutable length, including from a copy of the root's fixed part. Use the offset in the original block to locate the metadata. |

The arena aligns native blocks to 16 bytes. For a descriptor starting at
offset `o`, the location word starts at `(o + 8) & ~7`. For an aligned
descriptor, keep kind and length in their current positions. Otherwise
encode `(length << 4) | kind` in four bytes immediately after that word
when the word is at relative offset 1 through 3, and immediately before
it when it is at relative offset 4 through 7. All fields lie inside the
existing slot. Kinds 0 through 6 fit four bits. Byte length at most
268,173,376 and the separately bounded Records and Lookup counts fit 28 bits.
A prepared Null descriptor may have a nonzero pending length.
The location word is the only descriptor field that a physical move changes.
Inline offsets, count, stride, logical bytes and revision remain stable.
The incoming edge's acquire load precedes dereferencing the target.
The arena retains the previous target under its existing epoch protection.
See [Q35, point 4](../../open-questions.md#q35-what-the-root-layout-of-s05-leaves-to-later-sprints)
and [root-owned movement](../../../design/milestone-1-engine-contract.md#collections-and-strings).

Keep `ValueBlocks.Read` and `Write` for canonical scratch and transfer
bytes. Resident words and canonical payload words use the node's native
byte order. The layout version and the transport envelopes keep their
little-endian framing. A received descriptor passes the existing canonical
validation before conversion. When copying canonical bytes into a prepared native
root or record block, convert every descriptor before any fallible placement
or rollback walk. This includes inline, empty, zero and pending descriptors
in records that placement has yet to reach. Rollback reads the prepared
graph as resident storage from its first descriptor onward.

`BlockExport` reads each descriptor from the protected source and writes
all 16 canonical bytes, including for Inline and Null. The location used
by the export comes from a resident source load. A fixed-part copy from
`RootReader.CopyFixedPart` reads the resident metadata at the original block
offset, even when the copy is unaligned. It can read length without resolving
a native location. `BlockImport.FixedPart` is canonical scratch for the
scalar-key reader. Index entry byte layouts and the canonical bytes a
forwarded write sends retain their current forms.

Test all eight offsets with Null, pending Null, Inline, Block, Chunked,
Text, Records and Lookup. Use independently known byte positions to check
alignment, immutable metadata and adjacent storage after a location change.

Its stride is 19. An aligned holder puts the original location of its
second record at byte 62, crossing byte 64. Its chunk fits
`floor(65,504 / (19 + 64)) = 789` records. Exercise 788, 789 and 790
and preserve the maximum of 789 × 4,094, with an independent count check
at the maximum and its adjacent cases. Include the stride-23 case from
the reference harness. Check length from deliberately unaligned fixed-part
copy storage. Force a late import placement refusal after a nested value
has been placed and a Dictionary text acquired. Leave later inline,
empty or pending descriptors at unaligned offsets in the native copy.
Verify that rollback restores the block and text-reference counts.

### Collection tail proposal

Independent source review found that every changed Map or Set rebuilds
its lookup from the final count. Unchanged branches are adopted at the
same count. The reserve proposal gives a safe old slot to the same
collection's writer-owned cold list at normal FIFO retirement. The old
lookup holds it until its read epoch is safe. A published lookup never
probes a cold slot. A later sparse growth can take its slot, clear and
build its new payload under preparation, and return it to the cold
list on a failed preparation. Release due cold slots in bounded turns.
Keep prepared, reader-retired, eligible cold, active, class slack and
returned segment bytes distinct.

Keep the actual active span length at the needed range, so `Home` and
`Next` use one capacity for a complete probe. A contiguous holder uses
16 plus eight bytes per active slot in the payload. A slot block records
eight bytes per active slot, irrespective of its arena class. For the
same-sized examples above this avoids the active excess while counting
all 8,192 or 16,384 native bytes. Also compare preserving the existing
rounded active span where it fits the target and clipping only the
portion above twice need. This retains more of the current probe-load
behavior. Select from measurements of the normal lookup and growth paths.

The first feasible ownership key is the root generation and the flat
schema position of an existing collection addressed by sparse commands.
This includes flattened Owned fields. Whole assignment, reaching a
null field or deleting the root ends the lease. The ordinary prepare
path supplies the transfer state, so a bounded step need not grow a
registry. Limit the proposal to one former active lookup per owner and

## V2 text metadata memory model

This model compares two candidate layouts for 4,096 live text IDs on x64 CLR.
One distribution fills 64 leaves. The other leaves one ID in each of 4,096
consecutive leaves. The model assumes 16-byte object headers, 24-byte array
headers, 8-byte references and rounding to an 8-byte boundary. Let
`A(n, s) = align8(24 + n × s)` be the modeled size of an array.

Each locator leaf covers 64 possible IDs. The ordinary leaf occupies
`40 + A(64, 8) + A(64, 4) = 856` bytes. The compact leaf occupies
`48 + A(n, 8) + A(n, 4)` bytes for `n` allocated cells. The extra 8 bytes
hold the ID mask used to find a cell. A full compact leaf takes 864 bytes
and a compact leaf with one cell takes 112 bytes. Both layouts count
address words, writer slot ordinals and the live mask. A directory
uses five radix levels with 32 child references per branch. Each branch
occupies `32 + A(32, 8) = 312` bytes. The dense and scattered examples
use 6 and 135 branches respectively, plus a 32-byte directory object.
For arbitrary ID patterns, count the distinct branch prefixes at each level.

Both candidates use the same dense writer metadata. It takes

Each 64-slot page has 64 bytes of separation at each end for the fields
that change reference counts. A bucket page uses `56 + A(64, 4) = 336`
bytes. The current set has 1,024 heads and costs 6,984 bytes with its
directory. An old set with 8,192 heads adds up to 45,552 bytes. During
migration, count all pages still allocated in each set.
