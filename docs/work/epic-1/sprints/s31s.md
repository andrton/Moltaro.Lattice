# S31S · SQL Server provider

**Track:** full · **Needs:** S31 · **Before:** S32 · **Decisions:** O4, O9, Q09.6 ·
**Owner:** E06 · **Decided by:** the owner, 27 November 2026
([Q09.6](../../../decisions/persistence-backends.md#a-public-provider-contract-and-a-second-provider))

**Why here.** The owner decided on 27 November 2026 that durable storage is reached
through a public provider contract, and that this repository ships a second provider, for
Microsoft SQL Server. PostgreSQL stays the first provider and the production one. S27 to
S31 build the contract and its conformance tests with PostgreSQL. This sprint, built after
them, meets the contract of S27 to S31 once with a second server, and that tests the
boundary. Anything the second provider cannot meet without knowing PostgreSQL is a defect
of the contract, and it is corrected here for both providers. From S32 on, the shared
tests of durable storage run with both, and a sprint that extends the contract (S36,
S37) extends both providers.

- **Goal.** A Durable master runs on SQL Server with every guarantee it has on
  PostgreSQL: the shared tests of S27 to S31, conformance and scenario, pass for both
  providers, with no test changed for one of them.
- **Contract.**
  - New assembly `Moltaro.Lattice.SqlServer`. It depends on the contract, not on the
    engine, and owns `Microsoft.Data.SqlClient`. Its storage object for the options
    matches the one of PostgreSQL.
  - New test project `Moltaro.Lattice.SqlServer.Tests`. It runs the shared tests and
    tests what the provider keeps in its tables.
  - Exception X3 in the [exceptions register](../../exceptions.md) and the sentence of
    `AGENTS.md` on the test projects of the engine name the new test project.
  - The SQL Server lane of the [test lanes](../test-lanes.md) gets its CI job, which is
    added to the required checks in `.github/rulesets/main.json`. The image, the edition
    and the architecture of the server it runs on are chosen by the study.
  - If this sprint has to change the provider contract, the change is made for both
    providers and listed for the owner, as a draft contract allows before the first
    release.
- **To read.** [Q09.6](../../../decisions/persistence-backends.md); the briefs and records
  of [S27](s27.md) to [S31](s31.md); the [test lanes](../test-lanes.md).
- **Study.** Before step 1, bounded and read-only, with the licence of each source checked
  first. For each operation of the contract it asks how SQL Server provides it:
  - the leadership held by a session, and how the server notices a dead session;
  - a transaction that appends a group with its receipts and position;
  - the errors of the driver behind each class of failure: a definite rejection, an
    unknown outcome, the loss of the leadership;
  - writing and streaming saved units;
  - the isolation level each operation needs.

  The study also checks whether SQL Server runs on the rented ARM64 machine. Its report
  says what the provider uses and why.
- **Acceptance.**
  - The shared tests of S27 to S31 pass for both providers. A test that cannot pass on
    SQL Server is a finding about the contract, never a skip.
  - `Moltaro.Lattice.SqlServer` references only the contract and
    `Microsoft.Data.SqlClient`. No other shipped assembly references it, and a MemoryOnly
    instance loads none of it. A test states each.
  - The provider's tables live in a schema of their own and hold nothing but what its
    specification lists.
  - An unreachable server at open fails within its deadline with `Unavailable`.
  - A master whose leadership session is ended from outside commits no write after
    another master took the store.
  - The product documentation states what a SQL Server deployment needs: the
    permissions of the provider's login, and how fast the server notices a dead session.
- **Measured.** Reported, not judged, for both providers on the same workstation:
  - the early figure of S28, single small writes at 200 changes/s with 16 callers;
  - the reopen time of a master from base and tail, for the reference fixture.

  If SQL Server cannot run on the rented ARM64 machine, the timing figures there are for
  PostgreSQL only.
- **Out of scope.** Restore from a SQL Server backup: S36 exercises the backup with
  PostgreSQL, the production backend. Tuning SQL Server for production.
