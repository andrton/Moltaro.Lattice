How reads are protected: epochs and memory that is freed later

Moltaro.Lattice · an explanation, not a specification. The same text without the animation is in epoch-protection.md; the rule is in the arena protocol.

Status. Decided on 16 November 2026 and built in Epic 1, sprint S08, part 1, for reads by key and the primary index.

The idea

A writer never frees memory a reader might still be looking at. It puts that memory aside, and it is freed a moment later, once every reader that could have seen it has left.

Nobody waits: a reader does not wait for the writer, and the writer does not wait for readers. Step through one replace of an entity while two readers are at work.

Why this scales

  • The only thing a read writes is its own slot. No other reader writes there, so processors do not pass one piece of memory around, as they do with a shared lock.
  • The writer switches one pointer and goes on. It never waits for readers to finish.
  • The index is read the same way: an entry is one machine word, and a table that has to grow is built beside the old one, switched in, and the old table retired like an old state.

What an application can rely on

GuaranteeWhat it means
Nothing changes in the APINo call, option or error is added for this.
A read is coherent for one entityIt returns one written state, never a mixture. Several reads are still not a snapshot.
Reads and writes do not block each otherMore reading threads read more in total, up to the number of processors, and writes keep their pace. Any number of threads may write; their changes are published one after another, and “the writer” on this page is whichever of them is publishing at that moment.
A close is completeClosing waits for the reads in progress and frees everything.

What it costs

  • Old memory lives slightly longer: a small, bounded amount waits for the writer's next look at the readers. A read holds memory back only while it copies an entity; no application code runs and nothing waits while a read is inside.
  • Retired memory is counted and counts against the memory budget of the instance. A write that meets the budget first frees what can be freed.
  • It is not a snapshot and not versioning: an old state lives only until the readers that were already copying it are done.

A known technique

Nothing here is invented for this database. Protecting readers by epochs and freeing memory later is a long-established technique of operating systems and in-memory databases, usually called epoch-based reclamation.
