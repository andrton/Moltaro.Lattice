How a write is executed: one at a time, grouped at the persistence step

Moltaro.Lattice · an explanation, not a specification. The same text without the animation is in write-path.md; the rule is in the milestone contract. How reads are protected meanwhile: epochs.

Status. Decided on 17 November 2026 and built in Epic 1, sprint S09, part 2; the write batch on a master in sprint S17, part 2. A batch through a child and persistence in PostgreSQL are not built yet.

The idea

A write is prepared and published under one lock, one write at a time. Writes are gathered into a group only where something slow has to happen: at the persistence step.

Any number of threads may write; every write still takes its place in one order, its position. Step through one write when persistence takes no time, and then four writes when the persistence step is slow.

Two writes to one entity

A write is checked against the published state. While an entity has an earlier write that has not completed, a later write to it waits behind that one and holds nothing. Not completed means prepared and not published yet, or itself still waiting its turn. When the earlier write completes, published, refused or cancelled, the later one is checked against the state that is published then. So a later write never overtakes an earlier one. When persistence takes no time this happens only while a write refused for lack of memory is being settled: otherwise a write is published in the same hold of the lock that prepared it.

What an application can rely on

GuaranteeWhat it means
Order for one entityWrites to one entity are executed in the order their calls were made. A write that first waits for the position of its session takes its place when that wait ends. Calls that race on different threads have no order between them.
A write is wholeReaders see the state before a write or after it, never a mixture. So do they each member of a batch: no answer carries the position of the batch before all of it is visible, and a read that begins once its node has reached that position sees all of it. A search or an enumeration that runs while the batch is published may return some members as they were before it and others as after, as separate reads may.
Cancellation is honestBefore a write is handed to the persistence step, cancelling it withdraws it and leaves nothing behind. After that, the call returns what really happened.
Nothing is refused for being busyWrites that arrive faster than they complete wait their turn. A write is refused only when it does not fit into the memory of the database beside the stored data.
Reads are not held upA read takes no lock and goes on while writes run.

What it costs

  • Writes do not speed up with more writing threads: the work in memory is serial. Every database that keeps one order of writes in memory pays this; what scales with callers is the persistence step, through groups.
  • A very large entity holds other writes back while its values are encoded under the lock. Reads are not affected. Measured: one write of 32 MiB holds the lock for about 3 ms.
  • The lock is not fair: under many writing threads a single write can wait longer than the average. Measured at its worst: beside a caller that writes entities of 32 MiB one after another, a caller of small writes completed 1,500 to 4,300 a second where alone it completes about two million, and a single small write waited up to about 110 ms. A write that large gives its processor up once after it releases the lock; that helps and bounds nothing.
  • Measured in memory only, on the development machine: one calling thread replaces about 1.6 million entities a second, 16 threads about 1.0 million in total; reads by key on 16 threads beside them stay at about 15 million a second.

A known design

Nothing here is invented for this database. One writer at a time under one lock is how established embedded stores execute writes, and gathering the writes that arrive during a commit into the next commit is the group commit that database servers have used for decades.
